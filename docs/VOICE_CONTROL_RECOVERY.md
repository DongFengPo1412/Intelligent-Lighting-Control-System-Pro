# 现场反馈后的音频与语义控制修复

> 本文是历史实机音频基线。2026-10-23 新增连续轮次、可选 Wi-Fi PCM／实验性打断和小智适配的代码实现，见 [当前指南](PRO_FEATURES.md)；没有为新增路径进行实机听感验收。下列历史反馈不外推为新增功能的实测结果。

日期：2026-10-21。此记录接续 `INTERACTION_FIX_VALIDATION.md`；前期自动测试通过不能代替现场验收。

## 已确认的故障与修复

1. **播放任务栈溢出。** A/B/C 对比的 B 阶段实际日志出现 `A stack overflow in task audio_play_task has been detected`，随后重启。前一轮双声道转换增加了局部数组占用，播放任务仍只有 4096 字节栈。现在转换缓冲区改为 AudioHAL 成员，由播放互斥锁保护；任务栈增至 8192，和中阶音频输出任务一致。后续完整音频测试的最小剩余栈为 6056 字节。
2. **把电脑推送成功当成板端播放成功。** 旧 `play_audio_pcm()` 即使板子播放中崩溃，也可能返回 True。现在回执包含音频接收、成功写入 I2S、丢弃、错误及任务栈统计，电脑逐次比较采样增量；丢包、重启或写入错误不会被报告为完整播放。这里的“成功写入”仍不等同于声压或失真测量。
3. **新音频处理及增益造成听感回退。** 已撤回上轮新增的 RMS 压缩/软限幅及 90% 软件默认音量，恢复交接代码原有的语音处理和 75% 软件电平；板端默认恢复 70%。缓存版本改为 `original-v1`，不会复用 `clear-v2` 的新处理音频。唤醒回复恢复项目原有 PCM 文件。保留单一板载输出，避免电脑和板子重复发声。
4. **唤醒由带提示词的自由转写决定。** 原实现把名字提示给 Whisper，并接受很多近音词及短句子串。现改为独立声学关键词模型先检出，再做无提示词 ASR 确认；只接受句首的配置名称。没有声学证据时，Whisper 文字不能触发唤醒。对“助手/住手”等同音转写，仅在声学门已通过后修正书写；无法仅凭音频区分完全相同的发音。
5. **采音在转成 PCM16 前过度放大。** 原 32 位输入右移 12 位，转换前相当于加 16 倍增益。现场第一份原始录音约 23.7% 采样达到饱和值，影响识别。改为右移 16 位，电脑端做不超过 8 倍的有上限放大，VAD 能量门限相应调整；第二份原始录音的饱和值比例为 0。中阶使用 AFE/WakeNet，Pro 不能因为引用了中阶的整数转换就声称具有同样的前端能力。

## 现场听感对比及边界

- 用户确认“原有 PCM＋板端 70%”的人声与提示音恢复正常。
- 同一音源比较 70%、80% 和轻度带通，用户听感差别不明显。
- 两段全静音 PCM 在灯板亮、关闭两种状态下都安静；原人声仍有嗡感。不能据此确诊机械共振，但不支持把持续嗡声简单归因于灯板负载。
- 再比较 250 Hz、Q=0.8、-6 dB 的削减，用户仍听不出差别，因此不采用这层额外均衡，保留原样。
- 没有用测量麦克风或示波器测量扬声器频响、功放输出及电源纹波；残留嗡感可能涉及扬声器/腔体，但尚未确诊。

## 全模式语义控制

`semantic_control.py` 统一列出 0..25 中除 18 外的 25 个实际模式，包括关灯、单色、原灯效、表情、桌宠、频谱、反馈、游戏和结算、火焰、代码雨及带时长的倒计时。

明确的完整模式名称使用快速路径；其他话语交给真实本地 `kurisu` 模型，使用 JSON Schema 输出中文效果名及独立的时长、亮度、音量字段。效果名由程序映射到模式号，防止模型混淆数字编号或工具名。明确数值设置另按完整指令分句核对，避免复合句丢失亮度或音量；否定和疑问分句不会被当作数值指令。无效或矛盾计划允许模型修正一次，仍失败则不执行。不再从人格闲聊回复或广泛关键词中自动补发硬件动作。

控制只在板端确认后播报成功；普通聊天仍使用 Kurisu 人格模型，中日文本互译规则保留。控制确认语是准确的固定双语回执，普通聊天翻译失败不会用无关固定日语替换。音量工具和网页现在实际设置板端音量并等待回执，避免只改软件数值却对缓存唤醒音无效。

本轮完整模型测试 30/30，通过案例涵盖所有实际模式及否定、比较问句、情绪闲聊。示例：壁炉意象→23、水面扩散→10、绿色数字下落→24、不要红灯改星光→7；“红灯和蓝灯有何区别”和“今天很难过”不改灯。语义规划本身一般约 3.3 秒，完整播报时间更长，不能宣称任意措辞都正确或自然对话延迟已达标。

## 声学唤醒依赖与验证

- 声学门：Sherpa ONNX 的中文 Zipformer KWS，独立于 Whisper；在电脑运行，不宣称已经迁移为板载 WakeNet。
- 固定依赖位于 `pc-agent-vision/.runtime_deps`，版本见 `requirements-wake.txt`，未修改全局包。需要同时安装 wrapper 和 core 到同一目录。
- 模型位于忽略目录 `models/wake_kws`，来自官方 `kws-models` 发布中的 `sherpa-onnx-kws-zipformer-wenetspeech-3.3M-2024-01-01`，使用 epoch-12 INT8 encoder/decoder/joiner 及 tokens.txt。关键词文件由初始化生成。
- 配置词仅为助手、红莉栖、克里斯、牧濑红莉栖，取消小智及宽泛近音匹配。阈值使用 0.50；在已录真人音频上比较了 0.60/0.50/0.40，0.50 与 0.40 能检出两处，0.60 仅一处。
- 真人录音的一处“助手”经真实 KWS＋Whisper＋实际状态机离线回放，进入唤醒态并请求旧 PCM 应答；硬件输出替换为记录，没有再播放声音。
- 静音及此前背景录音没有命中。样本量很小，尚不能给出长期误唤醒率；完整服务仍需要用户现场复测。两音节“助手”天然比长短语更容易与同音话语混淆。
- KWS 加载失败会关闭自动唤醒，网页控制仍可用，不退回自由转写唤醒。

## 完整服务现场语音记录

本轮最后的真实板载麦克风操作：

1. 声学检测到“助手”，无提示词 ASR 写成“住手”；通过声学门后修正同音书写，正常播放原唤醒应答。
2. ASR“我想让东板向满天繁星来。”，平均 logprob 约 -0.344，采样削波比例 0；模型计划为模式 7，板端确认并播报“已切换为繁星点点”。
3. 再次声学唤醒；ASR“让水面起一圈圈剥文。”，平均 logprob 约 -0.455，采样削波比例 0；模型计划为模式 10，板端确认并播报“已切换为中心波纹”。
4. 随后查询：板端当前模式 10、音量 70%，音频接收及成功写入累计均为 361600 点，丢弃 0、错误 0、最小剩余栈 6056 字节，模型及音频错误为空，麦克风推流恢复。

这些日志证明了本次真实语音链路和两个语义场景完成执行；扬声器的新合成人声听感和长期误唤醒率仍以用户现场反馈及后续观察为准。

用户随后确认上述两个完整测试“完全没有问题”，并反馈当前每一轮交互仍需重新说“助手”。长期误唤醒率仍不能由这两次测试推定。

对中阶连续对话逻辑的核对：两个参考目录的 `main/application.cc` 内容相同。自动监听模式下，TTS stop 后由 Speaking 回到 Listening；音频通道关闭才进入 Idle，并恢复唤醒检测。Pro 当前在两条指令完成分支均直接设置 `is_awake = False`，因此是单轮唤醒行为；此次核对尚未修改这一交互策略。
