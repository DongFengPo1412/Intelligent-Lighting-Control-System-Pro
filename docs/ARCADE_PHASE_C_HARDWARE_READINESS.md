# Phase C — 首次实机部署与验收准备

这是部署前检查表，不是硬件通过记录。当前只完成源码、主机测试和构建；没有读取、刷写ESP32、清除NVS或安装手机APK。

## 1. 先确认设备与可恢复性

1. 人工确认ESP32-S3-N16R8、供电与USB串口。实际端口现场核对，不沿用历史COM号。
2. 记录当前运行固件版本、可用功能、Wi-Fi AP/STA状态和最高分。保留当前已知可工作的固件/bootloader/分区表及烧录参数。
3. 读取设备芯片/Flash容量与安全启动、Flash加密状态。若安全功能启用，先单列恢复方案，不套用普通迁移流程。
4. 检查旧设备实际分区表。仓库中的16MB配置不能证明板上已是同样布局。
5. 由用户明确批准后再开始设备操作。备份、写入、分区迁移和清除NVS不是本任务自动执行的一部分。

## 2. 备份与校验

- 备份文件放在仓库外的专属任务目录；完整Flash备份可能包含Wi-Fi凭据、配对密钥与用户数据，不上传GitHub。
- 确认容量确为16MiB后，再按所用esptool版本的`read-flash`/`read_flash`接口读取完整`0x1000000`字节；命令参数先用本地`--help`核对。
- 从实际旧分区表确定NVS地址、大小，另行备份对应区域。不要假设旧NVS一定在当前源码指定位置。
- 记录工具版本、端口、芯片、地址范围、文件字节数和SHA-256；重复读取可验证时比较哈希。保留原件，不覆盖旧备份。
- 备份存在不等于恢复已验证。需准备USB下载模式进入方法、可用数据线、驱动以及原固件完整恢复地址清单。

## 3. 当前项目布局与迁移闸门

当前`firmware-s3/partitions_16mb.csv`：

| 分区 | 偏移 | 大小 |
|---|---|---|
| NVS | 0x9000 | 0x6000 |
| otadata | 0xf000 | 0x2000 |
| phy_init | 0x11000 | 0x1000 |
| ota_0 | 0x20000 | 0x600000 |
| ota_1 | 0x620000 | 0x600000 |
| storage | 0xc20000 | 0x3d0000 |

若旧布局不同，禁止只把App BIN写到`0x20000`便假定可启动。先核对bootloader、分区表、OTA选择信息、NVS和storage占用，制定地址对照与回滚方案，再取得明确迁移授权。不要执行全片擦除来规避迁移问题。本任务没有改变上述布局。

先走串口恢复可控的部署；确认可回滚、应用槽大小和当前运行槽后，才考虑OTA。构建通过不等于已验证OTA更新、回滚或旧数据兼容。

## 4. 源码内存预算与新增观测

`idf.py size`约66%的DIRAM是静态链接占用，不能代表启动后的剩余堆。还有任务栈/TCB、Wi-Fi、TCP/IP、音频缓冲和碎片化等消耗。

| 应用任务 | 源码栈请求字节 |
|---|---:|
| main（本次sdkconfig） | 3584 |
| display_task | 8192 |
| arcade_sfx | 4096 |
| serial_cmd_task | 8192 |
| audio_play_task | 8192 |
| mic_stream_task | 4096 |
| wifi_udp_srv | 8192 |
| wifi_pcm | 8192 |

以上合计52736字节，尚不包括系统/空闲/Wi-Fi内部任务、临时提示音任务和分配器开销。`command_dispatcher.cc`另有32768字节播放ring buffer。PSRAM通用malloc已开启，内部优先阈值16384、内部保留32768；这些配置不证明所有DMA或任务栈都可由PSRAM替代。不要以Flash剩余81%判断RAM足够。

新增串口`RuntimeBudget`日志：启动完成后一次、之后每30秒一次，无额外任务：

- internal_free / internal_min / internal_largest：内部8-bit堆当前空闲、历史最低与最大连续空闲块。
- psram_free / psram_largest：PSRAM当前空闲和最大连续块。
- stack_min_bytes：main、display、sfx、pcm_play最小未用栈字节。本地ESP-IDF 5.5.4 `task.h`明确此API单位为字节。
- sfx queued/dropped/played/preempted/busy/short/late/faults：音效统计，需按阶段记录增量，不把语音优先抢占计为游戏逻辑错误。

UDP、麦克风、Wi-Fi PCM等任务的独立栈高水位仍需补充现场观测；当前日志没有宣称覆盖全部任务。启动日志中的分配/任务创建错误必须保留原文，不能以网页能打开判定整板资源正常。日志采集可能影响时序，延迟测量需注明采样条件。

## 5. 首次部署后的冒烟步骤

1. 先低亮度、普通灯效和桌宠启动，检查矩阵方向、末端灯珠和颜色。保留现有亮度20与功耗限制，不为拍照提高亮度。
2. 记录启动完成后的RuntimeBudget及错误日志，再分别测试AP和STA配对。令牌只在受控本地保存，不写入公开报告。
3. 人工批准安装签名APK，确认版本2.0.1/13。APK构建和浏览器测试不能替代安装及真实触控。
4. 在关闭PC服务后验证手机直连：选卡、开始、暂停、恢复、重开、退出；包含Mario向右+跳、松开跳保留右、Pong独立双人键。
5. 单独测试游戏音效，再与语音、音乐、麦克风依次切换。观察抢占、静音、恢复、断续及计数增量。
6. 断开Wi-Fi，检查500ms释键、1000ms暂停和重连后显式恢复。实际网络测试结果单独记录。
7. 写入一个真实合法高分并正常退出，重开验证；备份就绪后再安排断电/重新上电恢复检查，保留NVS异常日志。
8. 测试高密度/全白画面的真实供电电流、电压与温升。软件RGB限幅不等于电源实测安全。

## 6. 长时间和逐款验收

至少安排30分钟墙钟实测，包含100款轮换、快速组合键、反复暂停/恢复/退出、断连重连、语音/音乐/游戏切换。

记录每次切换的游戏ID、时间、异常、内部堆最低/最大块、PSRAM、栈最低值、音效计数与重启原因。关注随切换持续下降、最大连续块显著缩小、栈接近耗尽、分配失败或音频长期无法恢复等现象。加速主机模拟秒数不能替代这一步。

输入到LED延迟用可追溯的实机录像/时间戳方法测量，区分触控、UDP、逻辑步长、显示刷新和WS2812发送。60Hz逻辑更新不代表60FPS显示。

每款单独记录核心规则、玩家胜局/生存目标、失败、完整局、重开、三档难度、画面、手机、音效、得分/最高分、实机和最终品质。没有实测的一栏保留NOT_TESTED。当前没有任何一款被标为HARDWARE_PASSED或最终产品认证通过。
